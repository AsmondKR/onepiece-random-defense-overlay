## 1. 지금 TMO가 실제로 해주는 일 (측정으로 확정된 범위)

패 데이터는 이미 워크에서 직접 읽는다(유닛 풀·소유자·rawcode·인벤토리). 워크의
루트 복호화 산술도 이미 `TmoWarcraftDecoder`에 전부 이식돼 있다. TMO에서 오는 건
**딱 두 개의 64비트 값**뿐이다.

`TmoAssistedMemoryRecognitionService.ReadLiveRoots` 기준:

```
xorMask    = TMO 생성 디코더 코드(0x80바이트)의 오프셋 51 immediate
stateValue = TMO 메모리[generatorState + 0x30]
```

이 둘로 키를 만든다:

```
Key1 = seed1 ^ xorMask                 // seed1/seed2는 우리 코드의 하드코딩 상수
Key2 = seed2 ^ stateValue ^ xorMask
```

디코더에서 Key1·Key2의 실제 사용:

- **Key1**: `Key1 >> 52`(상위 12비트)와 `Key1 & 0xFFF`(하위 12비트)로만 쓰인다.
  즉 워크 이미지의 쿠키 테이블(`base + 0x2B58E00`)에 들어갈 **두 개의 12비트 인덱스**.
  실질 유효 비트는 24비트뿐.
- **Key2**: 복호화 중간값에 대한 **전체 64비트 XOR** 1회.

로컬 플레이어 루트는 이미 TMO 없이 정적으로 복호화된다(참고·중요):

```
root = [base+0x2B59964] ^ 0x363ABBFD3DEFAEC9 ^ [base+0x2BD7BC8]
```

→ **워크의 쿠키가 고정 RVA + 정적 매직으로 접근 가능하다는 증거.** GameUI/WorldFrame도
같은 성질일 가능성이 높다. TMO의 "코드 생성" 방식은 TMO 구현 취향(디코더를 JIT)일 뿐,
값이 매 실행 랜덤이라는 증거가 아니다. 원저자가 로컬 플레이어는 정적 매직까지 RE를
끝냈지만 GameUI/WorldFrame은 TMO 스냅으로 지름길을 택한 것으로 보인다.

## 2. 미지수와 판별 단계 (Determination) — RE의 유일한 실질 작업

우리가 모르는 것: **xorMask와 stateValue가 워크의 어디에서 오는가.** 세 가능성:

- (S) 고정 RVA에서 읽는 값(±정적 매직) → 하드코딩 또는 1회 읽기로 끝. **가장 유력.**
- (D) 워크 실행마다 달라지지만 워크 메모리에서 유도 가능 → 유도식을 이식.
- (R) TMO 내부 난수(워크와 무관) → 스캔 불가 → fail-closed(추천 중단). ~~현 구조 유지.~~ *(SUPERSEDED: §2 R-조항 대체됨)*

### 판별 방법 (TMO를 오라클로 사용)

개발 머신에서 TMO+워크를 띄운 상태로:

1. 현 서비스가 산출하는 `xorMask`, `stateValue`, `gameBase`를 로그로 캡처
   (진단 로깅만 추가하면 됨, 읽기 전용).
2. 캡처한 8바이트 값들을 **워크 프로세스 메모리에서 검색**해 등장 위치(RVA)를 찾는다.
   - `xorMask` 자체, `stateValue` 자체, 그리고 `값 ^ 알려진매직` 형태도 함께 검색.
3. **불변성 실험**으로 성질 확정:
   - TMO만 재시작(워크 유지) → 값이 그대로면 워크 파생(S/D), 바뀌면 TMO 난수(R).
   - 워크 재시작 → 값이 바뀌지만 **같은 RVA**에서 나오면 (S). RVA가 이동하면 시그니처 앵커 필요.
   - 재부팅 후 반복.

결과가 (S)/(D)면 스캐너 성립. 이 판별은 반나절 규모이며 **한 번만** 하면 된다.

## 3. 런타임 설계 (성능 최우선)

인식 틱의 비용은 ①루트 해석 ②유닛 풀 열거로 나뉜다. ②는 v0.4.23에서 이미 클러스터
블록 읽기로 최적화됨. 이 설계는 ①만 바꾸며, **정상 상태 틱이 지금보다 싸진다**.

### 3.1 원칙: 붙을 때 1회 해석, 세션 내내 캐시

- 워크 프로세스에 처음 바인딩할 때 (pid, base, 파일버전) 키로 xorMask·stateValue(또는
  그 소스 RVA)를 **1회 해석**하고 바인딩 캐시에 보관.
- 프로세스/베이스가 바뀔 때만 무효화.
- → 틱당 루트 해석 = 워크에서 ReadUInt64 2~4회 + 순수 산술. **스캔 없음.**
  (현재는 틱마다 TMO 생성 코드 0x80B 재읽기 + 서명 재검증까지 하므로 이보다 비쌌다.)

### 3.2 주소는 전부 시그니처 앵커 (하드코딩 RVA 금지)

지금 `0x2B58E00`(테이블), `0x2BDAB70`(암호화 GameUI), 로컬 플레이어 쿠키 RVA 등이
전부 하드코딩이라 **워크 패치 한 번에 전부 깨진다**. 이걸 워크가 패치돼도 자가 치유되게:

- 각 접근점을 `.text`/`.rdata` 안의 **바이트 시그니처(와일드카드 포함)**로 찾는다.
  기존 `GeneratorSignature`가 TMO에서 하던 방식을 워크 대상으로 이식.
- 스캔 범위는 전 주소공간이 아니라 **모듈 섹션으로 한정**(수십 MB). `Span.IndexOf`
  단일 전방 패스면 <50ms, 그나마 붙을 때 1회.

### 3.3 빌드 해시 키 영구 캐시 (콜드 스타트도 빠르게)

- 워크 파일버전/해시별로 해석된 RVA 집합 + 검증 체크섬을 `%LOCALAPPDATA%`에 영구 저장.
- 이후 실행: 저장된 RVA로 **즉시 읽기** → 아래 유효성 게이트 통과하면 스캔 자체를 생략.
- 게이트 실패(=워크 패치로 RVA 이동) → 그때만 재스캔 후 캐시 갱신. 자가 치유.

### 3.4 신뢰 대신 유효성 게이트

복호화한 GameUI/WorldFrame을:

- 플러시블 유저 주소인지
- GameUI 객체의 RTTI 클래스가 기대값인지(이미 있는 `HasExactMsvcClass` 재사용)
- WorldFrame이 GameUI에서 도달 가능한지, 풀 카운트가 검증 범위인지

로 확인. 실패 시 키를 stale 처리하고 재해석. 캐시가 드리프트해도 쓰레기를 읽지 않고
즉시 감지한다. **fail-closed 유지**(기존 정책과 동일).

### 3.5 TMO 측 완전 제거

`Process.GetProcessesByName("TMO.GG")`, TMO 프로세스 열기, TMO 사설 영역 vtable 전수
스캔(현 구조에서 가장 비싼 단일 스캔)이 전부 사라진다. 붙을 때·정상 상태 모두 큰 이득이며,
오늘의 버그 계열(다중 프로세스, TMO 버전 고정, TMO 권한 결합)이 원천 소멸.

## 6. 리스크와 유지보수

- (R) 가능성(값이 TMO 난수)이 판별에서 확인되면 스캐너 불가 → ~~현 구조 유지.~~ *(SUPERSEDED: §6 R-조항 대체됨)*
  **대체 정책**: R-케이스 라이브 판별 세션 최대 2회 소진 후 루트 유도 실패 시, 코드 정리 및 fail-closed를 최종 산출물로 확정. TMO 의존으로 후퇴하지 않는다.
- 워크 패치 시 시그니처가 깨지면 재작성 필요. 단 시그니처 앵커 + 빌드 해시 캐시로 "코드 패턴이
  같고 위치만 이동"한 경우는 자가 치유. 지금도 워크 버전 고정이라 마이너스가 아니라 개선.
- 안전 원칙 불변: PROCESS_VM_READ만, 쓰기·주입·후킹 금지. 네이티브 전환은 읽는 대상이
  TMO→워크로 바뀔 뿐 읽기 전용 성격은 동일.

## 7. 단계 계획

1. **판별 실험**: 진단 로깅 추가(xorMask/stateValue/gameBase) → 개발 머신 TMO+워크로
   값 캡처 → 워크 메모리 검색 → 불변성 실험으로 (S/D/R) 확정. **여기서 성패가 갈린다.**
2. (S/D 확정 시) **네이티브 디코더 구현**: 시그니처 앵커 리졸버 + 빌드 해시 캐시 +
   유효성 게이트. 순수 산술은 기존 `TmoWarcraftDecoder` 재사용.
3. **단일 경로** 릴리스: 네이티브 직접 스캔만, 진단에 상태 표시. 스모크 테스트 추가.
4. 코드에서 TMO 브리지 완전 제거 + 버전 고정 완화.
